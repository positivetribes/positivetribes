# Tribe Hub notes (loaded only when working in hub/)

Moved from ~/.claude/CLAUDE.md to save tokens on every request. Global rules (security, Salesforce logging, email, subagent models) still apply.

The hub is Positive Tribes' one shared workspace for every client and for Eric's own command center. Know how it works, use it as a source of truth next to Salesforce, and keep this section accurate.

- **What it is:** a Cloudflare Worker named `tribe-hub` (code in `/Users/eroberts/Projects/PositiveTribes/hub/`, with `hub/README`-style notes in `PositiveTribes/README.md`). Static single-page app in `hub/public/` (`index.html`, `command.js`) with hash routes, API in `hub/src/` (`index.js`, `admin.js`, `notifications.js`, `salesforce.js`, `access.js`). No workers.dev address; it is only reachable at hub.positivetribes.org.
- **Sign-in:** Cloudflare Access with One-time PIN. People are matched by email to the `users` table (roles: `ed` = client executive director, `staff` = client staff, `pt` = Positive Tribes, all clients). The daily sync routine uses an Access service token and may call only `GET /api/admin/match` and `POST /api/admin/activity`.
- **Client side** (`#/<client-slug>/...`): *What's next* (home: project phases, releases, testing windows, documents), *Questions & changes* (the backlog: questions, changes, problems, requests, each with tier must/nice/idea, phase review/prototype/full/later, owner, answer, due date, done, UAT sign-off), and *Improve this hub* (ideas, with Positive Tribes replies; opened from the lightbulb button in the top bar). A bell shows notifications (added, answered, done, phase moves, sign-offs, UAT started, live, shared documents, idea replies; testing-window-ending reminders pinned). On the home page, a project with several client phases spans the row with its phases side by side, and the others sit beneath; "all caught up" is one slim line. A *System status* card on a client's home (one folded line, "All systems running", while every check is up; the full card when anything is not) shows live up/down and 90-day uptime for that client's apps, fetched server-side from the `tribe-status` Worker's public JSON (`GET /api/c/<slug>/status`, `STATUS_URL` var; empty if the client has no checks). Old backlog sites (UEP, Project Coyote) now forward here and refuse changes (`MOVED_TO`); their databases are kept for history.
- **Care plans (P1, live since 2026-11-05 via migration 0015; UEP's plan row exists in status setup, tier Care, 6 credits, added 2026-11-09; no plan is active yet):** one plan per client (`care_plans`: Essentials 2 / Care 6 / Growth 12 credits a month), an append-only `credit_ledger` (grant, boost, spend, refund, courtesy; balances are computed, never stored; unused monthly credits roll over one month; boost packs last 12 months and are used last), and `care_requests` (a side row on a backlog item of kind `request`). Projects carry `salesforce_opportunity_id` and `opportunity_won`, set only by the Worker after reading the Opportunity from Salesforce and checking it is on the client's own Account. "Request an improvement" opens only for a tool that is closed-won and in phase `support` on an active plan; a plan can only be active when its go-live checklist is complete. Positive Tribes sorts each request (fix = free, courtesy edit = always free since 2026-11-10, improvement S/M/L = 1/2/4 credits, new project = quoted separately); credits are used only when the director or the one named contact confirms. Only the director, that contact and Positive Tribes see balances and credit history (enforced in `src/care.js`); staff see status, size and cost; event details never carry a balance. Routes: `GET /api/c/:slug/care`, `POST /api/c/:slug/care/:itemId/(triage|confirm|decline|ship|cancel)`, and for Positive Tribes `GET /api/admin/care`, `PUT /api/admin/care/:clientId`, `POST /api/admin/care/:clientId/boost`, `PUT /api/admin/projects/:id/opportunity`; the overview is `#/command/care`. All client writes now require `Origin` to match the hub. Build rules: `care-plan-build-playbook` memory.
- **Patch triage (P2a, deployed 2026-11-07 with migration 0016, merged to main in PR #114; `ANTHROPIC_API_KEY` set 2026-11-07 from the Claude Console "Positive Tribes" org, workspace "Patch" ($25/month limit, org limit lowered, no auto-reload), key "tribe-hub" expires 2027-11-07, renewal reminder on Eric's calendar Oct 24, 2027):** Patch, the hub's AI helper, suggests how to sort each new care request; the Tribe Guide agrees or changes it, so nothing reaches a client without Eric's tap (trust levels are capped at 1 in code). Code in `hub/src/patch.js` (rules, rule-1 word screen, Anthropic call, scoring, trust, admin routes) and `hub/src/triage.js` (shared `applyTriage`, `askQuestion`). Tables (migration 0016): `triage_rules` (per-client extra rules, versioned; the standard five questions live in code as `standard-2` since 2026-11-10), `patch_decisions` (each suggestion, the Tribe Guide's answer, miss score, tokens and cost), `trust_levels`, `trust_changes` (append-only), `patch_models` (exact model id per job, with rollback), `patch_runs`; `care_requests` gained question/answer columns ("Needs more info": one question to the client, any of their people answers, Patch checks again). A daily cron (`0 12 * * *`) and "Run Patch now" run it, only where `PATCH_HOST` is `hub.positivetribes.org` and the `ANTHROPIC_API_KEY` Worker secret is set; manual runs also check the request host so previews never call the API. Only the request's own text goes to the API (emails and phones masked, no names or balances); a request that hits the rule-1 word screen (sign-in, payments, permissions, health or personal data) is never sent and goes to the Tribe Guide as a screened check. Trust per kind (fix, courtesy, improvement S/M/L, needs info): promotion needs 30 decisions, 95% agreement over the last 30, no serious miss in 60 days and 2 clients; a serious miss or agreement under 90% demotes automatically; at level 0 every check is blind, otherwise 1 in 5. New projects and rule 1 are never automated. Routes (pt only): `GET /api/admin/triage`, `POST /api/admin/triage/run`, `POST /api/admin/triage/:id/(decide|reason)`, `PUT /api/admin/trust/:kind`, `GET|PUT /api/admin/rules/:clientId`, `PUT /api/admin/models/:job`, `POST /api/admin/models/:job/rollback`; client `POST /api/c/:slug/care/:itemId/answer`. Screen: `#/command/care/triage`, the Triage sub-tab of Care plans (queue, trust, client rules, models, AI cost; the old `#/command/triage` forwards there). P2b (paused): draft offer and Opportunity, monthly Salesforce summary. Shelved 2026-11-10: auto levels 2-3, rule-edit replay, new-model loop.

- **Patch reply drafts (migration 0024):** on a suggested change or test problem, Positive Tribes sees "Draft a reply with Patch" in the reply editor. Patch (job `writing`, Sonnet 5.5 set in `patch_models`, changeable in the command center) drafts a reply of 600 characters or fewer plus a suggested status; Positive Tribes edits and saves, so nothing reaches a client by itself. Code in `hub/src/reply.js` (`POST /api/admin/items/:id/draft-reply`, `POST /api/admin/replies/:id/sent`, `GET|PUT /api/admin/facts/:clientId`). It sends only that item's masked text, its kind, tier and phase, and that client's facts sheet: the `client_facts` table (versioned, newest in use, separate from `triage_rules`), edited under Care plans > Triage > "What Patch may say". No facts, no drafts. Items with rule-1 words are never sent. A draft that states a price, date, hours or credits is thrown away in code. A declined or unsure draft is marked "check carefully". Each draft is logged in `patch_replies` (tokens, cost, and what was finally saved, so we can see how often it goes out unedited); 40 drafts a day at most; production host only. Facts sheets are client data: loaded by SQL, never in code or git.
- **Items ride a release (migration 0025):** `items.release_id` (pt-only via PATCH, same client and list, cleared when the item moves list) is the phase a change/problem ships in. - **Change estimates (migration 0026, built 2026-11-09, plan in `docs/change-estimates-plan.md`):** for a suggested change (`kind` change) outside the agreement, Positive Tribes enters hours only (half-hour steps, 0.5 to 200) in the estimate box on the card; price = hours x the client's `clients.hourly_rate_cents` (default 5000, change it with `UPDATE clients SET hourly_rate_cents = ... WHERE id = ...` on `hub-db`, or `PUT /api/admin/clients/:id/rate`) and credits = hours x 2 (1 credit = 30 minutes), both copied into `change_estimates` when sent so a later rate change never alters a sent or approved estimate. A draft is Positive Tribes' alone; "Send to client" rings the client's bell (`estimate_offered`). Everyone on the client's hub sees the price; only the director (`ed`) or the care plan's named contact gets the buttons **Add it now** (item becomes Planned, Full build), **After launch** (Planned, Later; only if the client has a care plan row that is not ended and the change is 2 hours or less, the largest care size) and **Not now** (stays on the Wishlist; a Must have becomes an Idea). Positive Tribes never decides (403). Re-estimating bumps `version` and a decision names the version it saw, so a stale one is refused (409); the decision is one batch guarded by `decided_token`, so a double click decides once and logs one `estimate_decided` event (that event reaches Positive Tribes' Inbox and the client's other people). Approving (not Not now) creates one Salesforce Task on the project's `salesforce_opportunity_id` (client Account if none) due in 7 days, using the existing Task-write access only (no Opportunity writes: adjust the amount by hand); on failure `sf_error` is stored, Today shows it, and `POST /api/admin/items/:id/estimate/retry-task` retries. Pull request previews never write Tasks (`SF_TASK_SYNC_HOST`). Today lists estimates waiting (folded to one line per client: count, hours, value, donated share, oldest; rust when the oldest is 7+ days; open it for the items) and approved changes to bill and schedule ("Billed and scheduled" sets `handled_at`). Code in `src/estimates.js`; routes: `PUT /api/admin/items/:id/estimate`, `POST .../estimate/(offer|withdraw|handled|retry-task)`, `GET /api/admin/estimates`, client `POST /api/c/:slug/items/:id/estimate/decide`. Patch never sees an estimate and never states a price. Approving after launch does not yet become a care request by itself: Eric converts it when the tool is live (Today keeps it listed). While an estimate is offered, clients can't mark the item done, change its phase or move it to another list (UI hides Mark done and When; the server returns 409); Positive Tribes keeps every control and Withdraw releases it. Each estimated card carries a pill in its top row (Draft estimate, Estimate sent · N days, Approved, Approved · donated, Not now, Withdrawn; drafts and withdrawn are Positive Tribes' only); no pill means not estimated. With no estimate, "Estimate" is a button in the card's action row (Positive Tribes only). Positive Tribes gets an "Estimate" filter beside Show on Suggested changes (Any, Not estimated, Draft, Sent, Decided). An estimate can carry a breakdown (migration 0028, `change_estimates.lines`, JSON of {label, minutes}, up to 8, labels 120 chars): with lines, the hours are their sum; clients see it folded as "What's included (N parts)" once sent. Write lines in the client's words (what they get); internal reasoning stays out. The estimate form shows a refused save inside the form and checks lines (description, 120 characters, hours) before sending (PR #149). A change the signed agreement already covers is marked with its requirement IDs (migration 0029, `items.agreement_ref`, e.g. "F7" or "R12, R13"; More options > In the agreement, Positive Tribes only): everyone sees an "In the agreement · F7" pill, it drops out of Not estimated into the Estimate filter's "In the agreement", the Estimate button hides, an estimate can't be saved while it is marked (409), and it can't be marked while a non-withdrawn estimate exists. Logs a `covered` event (not on the client's bell). IDs come from the project's requirements file (`kits/requirements.md`).
