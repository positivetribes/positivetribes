# Tribe Hub notes (loaded only when working in hub/)

Moved from ~/.claude/CLAUDE.md to save tokens on every request. Global rules (security, Salesforce logging, email, subagent models) still apply.

The hub is Positive Tribes' one shared workspace for every client and for Eric's own command center. Know how it works, use it as a source of truth next to Salesforce, and keep this section accurate.

- **What it is:** a Cloudflare Worker named `tribe-hub` (code in `/Users/eroberts/Projects/PositiveTribes/hub/`, with `hub/README`-style notes in `PositiveTribes/README.md`). Static single-page app in `hub/public/` (`index.html`, `command.js`) with hash routes, API in `hub/src/` (`index.js`, `admin.js`, `notifications.js`, `salesforce.js`, `access.js`). No workers.dev address; it is only reachable at hub.positivetribes.org.
- **Sign-in:** Cloudflare Access with One-time PIN. People are matched by email to the `users` table (roles: `ed` = client executive director, `staff` = client staff, `pt` = Positive Tribes, all clients). The daily sync routine uses an Access service token and may call only `GET /api/admin/match` and `POST /api/admin/activity`.
- **Client side** (`#/<client-slug>/...`): *What's next* (home: project phases, releases, testing windows, documents), *Questions & changes* (the backlog: questions, changes, problems, requests, each with tier must/nice/idea, phase review/prototype/full/later, owner, answer, due date, done, UAT sign-off), and *Improve this hub* (ideas, with Positive Tribes replies). A bell shows notifications (added, answered, done, phase moves, sign-offs, UAT started, live, shared documents, idea replies; testing-window-ending reminders pinned). A *System status* card on a client's home shows live up/down and 90-day uptime for that client's apps, fetched server-side from the `tribe-status` Worker's public JSON (`GET /api/c/<slug>/status`, `STATUS_URL` var; empty if the client has no checks). Old backlog sites (UEP, Project Coyote) now forward here and refuse changes (`MOVED_TO`); their databases are kept for history.
- **Care plans (P1, live since 2026-11-05 via migration 0015; no client plan set up yet):** one plan per client (`care_plans`: Essentials 2 / Care 6 / Growth 12 credits a month), an append-only `credit_ledger` (grant, boost, spend, refund, courtesy; balances are computed, never stored; unused monthly credits roll over one month; boost packs last 12 months and are used last), and `care_requests` (a side row on a backlog item of kind `request`). Projects carry `salesforce_opportunity_id` and `opportunity_won`, set only by the Worker after reading the Opportunity from Salesforce and checking it is on the client's own Account. "Request an improvement" opens only for a tool that is closed-won and in phase `support` on an active plan; a plan can only be active when its go-live checklist is complete. Positive Tribes sorts each request (fix = free, courtesy edit = free up to 5 a month then 1 credit per 5, improvement S/M/L = 1/2/4 credits, new project = quoted separately); credits are used only when the director or the one named contact confirms. Only the director, that contact and Positive Tribes see balances and credit history (enforced in `src/care.js`); staff see status, size and cost; event details never carry a balance. Routes: `GET /api/c/:slug/care`, `POST /api/c/:slug/care/:itemId/(triage|confirm|decline|ship|cancel)`, and for Positive Tribes `GET /api/admin/care`, `PUT /api/admin/care/:clientId`, `POST /api/admin/care/:clientId/boost`, `PUT /api/admin/projects/:id/opportunity`; the overview is `#/command/care`. All client writes now require `Origin` to match the hub. Build rules: `care-plan-build-playbook` memory.
- **Patch triage (P2a, deployed 2026-11-07 with migration 0016, merged to main in PR #114; `ANTHROPIC_API_KEY` set 2026-11-07 from the Claude Console "Positive Tribes" org, workspace "Patch" ($25/month limit, org limit lowered, no auto-reload), key "tribe-hub" expires 2027-11-07, renewal reminder on Eric's calendar Oct 24, 2027):** Patch, the hub's AI helper, suggests how to sort each new care request; the Tribe Guide agrees or changes it, so nothing reaches a client without Eric's tap (trust levels are capped at 1 in code). Code in `hub/src/patch.js` (rules, rule-1 word screen, Anthropic call, scoring, trust, admin routes) and `hub/src/triage.js` (shared `applyTriage`, `askQuestion`). Tables (migration 0016): `triage_rules` (per-client extra rules, versioned; the standard five questions live in code as `standard-1`), `patch_decisions` (each suggestion, the Tribe Guide's answer, miss score, tokens and cost), `trust_levels`, `trust_changes` (append-only), `patch_models` (exact model id per job, with rollback), `patch_runs`; `care_requests` gained question/answer columns ("Needs more info": one question to the client, any of their people answers, Patch checks again). A daily cron (`0 12 * * *`) and "Run Patch now" run it, only where `PATCH_HOST` is `hub.positivetribes.org` and the `ANTHROPIC_API_KEY` Worker secret is set; manual runs also check the request host so previews never call the API. Only the request's own text goes to the API (emails and phones masked, no names or balances); a request that hits the rule-1 word screen (sign-in, payments, permissions, health or personal data) is never sent and goes to the Tribe Guide as a screened check. Trust per kind (fix, courtesy, improvement S/M/L, needs info): promotion needs 30 decisions, 95% agreement over the last 30, no serious miss in 60 days and 2 clients; a serious miss or agreement under 90% demotes automatically; at level 0 every check is blind, otherwise 1 in 5. New projects and rule 1 are never automated. Routes (pt only): `GET /api/admin/triage`, `POST /api/admin/triage/run`, `POST /api/admin/triage/:id/(decide|reason)`, `PUT /api/admin/trust/:kind`, `GET|PUT /api/admin/rules/:clientId`, `PUT /api/admin/models/:job`, `POST /api/admin/models/:job/rollback`; client `POST /api/c/:slug/care/:itemId/answer`. Screen: `#/command/care/triage`, the Triage sub-tab of Care plans (queue, trust, client rules, models, AI cost; the old `#/command/triage` forwards there). P2b (later): auto levels 2-3, rule-edit replay, new-model loop, draft offer and Opportunity, monthly Salesforce summary.
- **Positive Tribes side** (`#/command`): command center with *Today*, *Inbox* (Positive Tribes' bell), *Clients* (`#/command/client/<id>`: Salesforce records plus notes, next steps, synced email/meeting activity), *Care plans* (sub-tabs Overview and Triage; the tab's count is Patch suggestions waiting, `carePending` on the overview), *Documents*, and *Improve this hub* as a separate link at the right end of the menu (ideas queue; `npm run next-build` in `hub/` lists ideas with status `next`). "Preview as" lets Eric see a client person's view and bell read-only. `/admin` on positivetribes.org redirects here.
- **Data:** D1 `hub-db` (clients, users, projects with phases, items, events log, releases, documents, ideas and screenshots, notifications; migrations in `hub/migrations/`, apply with `npm run migrate`) and D1 `positivetribes-admin-db` (command center notes, next steps, synced activity, sync history). Every client-owned row carries `client_id`; one database serves all clients. PR previews use separate `*-preview-db` databases.
- **Status pages:** `tribe-status` Worker (code `/Users/eroberts/Projects/PositiveTribes/status/`, D1 `status-db`, status.positivetribes.org/<client> and `/<client>.json`, public, names and up/down only). A one-minute cron probes each client's health URL; clients and checks are entries in `status/src/config.js` (deploy with `npm run deploy` in `status/`). Kuma on the home server stays the private alerting tool.
- **Backups:** `tribe-backup` Worker (code `/Users/eroberts/Projects/PositiveTribes/backup/`, deployed 2026-11-08, R2 bucket `tribe-backups`, secret `BACKUP_KEY` kept in Vaultwarden; first backup and restore drill passed; deploy changes with `npm run deploy` in `backup/`). A 08:00 UTC cron dumps `hub-db`, `positivetribes-admin-db` and `uep-scheduler-db` as SQL, gzips, encrypts (AES-256-GCM) and stores them in R2 for 30 days; `backup.positivetribes.org/health/<client>` says only ok or stale. UEP's System status shows a "Nightly backup" row (the `backup` check in `status/src/config.js`); add the same check and the client's databases in `backup/src/config.js` (`CLIENT_CHECKS`) for each new client. Restore steps are in `backup/scripts/decrypt.mjs`. D1 Time Travel is the first line of recovery; this is the longer-lived copy (30 days of dated files). It lives in the same Cloudflare account, so it does not cover losing the account.
- **Salesforce link:** the Worker reads Salesforce (client-credentials secrets `SF_DOMAIN`, `SF_CLIENT_ID`, `SF_CLIENT_SECRET`) and syncs the command center's next steps with Salesforce Tasks, owned by Eric, written only from the production host. Salesforce stays the source of truth for accounts, contacts, opportunities.
- **Operating it:** deploy with `npm run deploy` in `hub/`, test with `npm test`. Production data is real: before changing hub data or schema, look at the target first; write schema changes as a new numbered migration; never run test edits against `hub-db`. To change a backlog item (done, answer, phase, tier, due date, title, details), use `npm run item -- <client-slug> <id> [--done|--reopen] [--answer "..."] [--phase ...] [--tier ...] [--due YYYY-MM-DD|none] [--title ...] [--details ...]` in `hub/` (dry run; add `--apply` to write). It writes the matching `events` rows the app writes, and the client's bell is built from `events`, so hand-written SQL that skips them misses notifications.
- **Keep it current:** when work in a session adds, moves or changes a hub client, project, release, document, item or idea, update the hub as part of the task (not an afterthought) and tell Eric in one short line what changed. Don't ask first. The hub sits behind Access, so Claude can't fetch it directly: use the code, the D1 databases (via Cloudflare), or the sync routine. When the hub's structure or behavior changes (new views, roles, tables, routes, integrations), update this section in the same session and say so in one line. The hub is also a reusable product: track it in the Productization Strategy doc's Build inventory.
- **Every document shared with a client goes in the hub:** whenever a proposal, agreement, test script, design or any other document is sent or shared with a client (an email attachment counts), add or update its row in the hub's `documents` table (`hub-db`, via `npx wrangler -c wrangler.jsonc d1 execute hub-db --remote` in `hub/`) in the same session, before calling the task done. Set the right `client_id`, `project_id` (NULL until a project exists), `kind`, a plain `title`, a `note` with what was sent, to whom and when, and `status` `sent`. Use the same file the client received (the PDF, not an editable Doc) with a link they can open, and confirm with Eric that it is shared with them before setting `visible` to 1. When the client signs, set `status` to `signed` and update the note. Look at the target first (check for an existing row), and tell Eric in one line what changed. Don't ask first.
- **Closed Won means a hub card:** when a client's Opportunity is Closed Won, build its project card in the hub in the same task (a `projects` row with the right phase, its signed proposal and other documents linked by `project_id`, then set the Salesforce Opportunity on the project from `#/command`) and tell Eric in one line. Don't wait to be asked. (Rule stated by Eric 2026-11-08, when the UEP Virtuous to Salesforce card was missing.)
